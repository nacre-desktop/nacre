# N0044 — `wallpaper.active` motion member

Status: **Implemented; pending lead review**. Consumer: Bead B0046 (video wallpaper,
`docs/specs/0046-dynamic-wallpaper.md` on Bead main), which already parses and validates the member
(`wallpaper::parse_motion`). Additive: optional field, no version bump, QML unchanged, unpublished.

## Contract

When the active wallpaper is a video or an animated GIF, each pair (`current` and every `outputs` entry)
gains

```json
"motion": {"kind": "video" | "animation", "path": "/abs/clip.mp4", "file_identity": { ... }}
```

`path`/`file_identity` of the pair stay the cached still poster (the fallback while the decoder is released).
`motion` is **absent** for still wallpapers. `kind` is `animation` for animated GIFs, else `video`.
`motion.path` follows the poster's path rules (absolute, no `..`, no `://`, <= 4096 bytes).
`file_identity` is the same tuple as the poster's (`device`, `inode`, `size`, `mtime`, `ctime`) taken from the
opened file. Types: `nacre_protocol::wallpaper::{WallpaperMotion, MotionKind}`; schema
`protocol/schema/wallpaper-active*.json`, Luau `protocol/luau/wallpaper-active.d.luau`, golden
`protocol/fixtures/wallpaper-active.jsonl` (second pair carries a video) are generated by
`cargo run -p nacre-protocol --example export`.

One change to the existing shape: `WallpaperFileIdentity.size` is now bounded by the safe integer (was 128 MiB)
because video files are larger. The poster stays capped at 128 MiB by `ActiveWallpaper::validate`
(`POSTER_BYTES`), so poster behaviour is unchanged. Older consumers that deserialize the identity without
validating keep working; unknown optional members are ignored.

## Producer

`daemon/active_wallpaper.rs::read_motion` reads private `state/wallpaper/media.json` (the existing
selection record, which Bead never reads) and publishes motion only when `media.poster ==
presentation.poster` and `dynamic == true`. The video is opened with the same `private_file` checks as the poster
(no symlink at any component, user-owned regular file, no group/world-writable ancestors, readable) with a 64 GiB
sanity cap instead of 128 MiB. Any failure leaves the still wallpaper without `motion`; it never makes the pair
unavailable. A motion change is a new pair, so the revision increments (the fingerprint covers `motion`), and
the next published pair replaces or removes the member.

`presentation.json` is committed before `media.json` when a wallpaper is applied, so the daemon's wallpaper watcher
now also watches `state/wallpaper/` and re-reads the pair when `media.json` changes (daemon bit only, no legacy
generation). Without that the video would be missed whenever the first refresh ran in between the two writes.

## Checks

Unit tests with a temp HOME and generated fixtures: still has no member; video and GIF publish the member with a
matching identity on all outputs; unchanged inputs keep the revision; another poster, symlink, missing file and
group-writable file give no member; going back to a still removes it. Protocol tests: optional member, path
rules, poster cap vs. motion size, unknown kind rejected. Watcher test: `media.json` sets the daemon bit only
with presentation enabled.
