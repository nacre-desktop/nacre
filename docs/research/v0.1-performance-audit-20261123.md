# v0.1 performance audit (2026-11-23)

The question (owner, 2026-11-23): how optimized is Nacre, and would we call it highly
optimized? This audit answers with numbers against stated targets. It also explains how
the daemon is built.

**Short answer:**
- At rest and at launch, yes. In controlled runs, Nacre is leaner than the shell we benchmark
  against (Noctalia) on idle CPU, idle wakeups, memory before first use and launch time.
- In motion, not yet. Interaction costs about 5x Noctalia's CPU, because Nacre draws on the
  CPU and Noctalia on the GPU. Large-panel animations miss the 120 Hz budget in about one
  slide in six. Memory grows about 43 MiB after first use.
- "Lean at rest, not yet highly optimized in motion." The remaining costs are named below
  with their owner.

### What the live numbers mean

- **The open Today pearl.** The floating Today pearl restored from `pearls.json` keeps the
  `dashboard.system` sampler running: 62 publishes a minute, about 64,300 since 00:44. Each
  publish wakes the shell to project new gauges. Since 20cc923a0 a publish that changes no
  visible digit restages nothing. With no pearl, the daemon stops sampling: its samplers run
  only while someone subscribes.
- **nacre-niri is mostly its clients.** Its main thread wakes 49 times a second at about 5 %
  CPU while nobody types. It composites every commit: the streaming terminals, the pearl's
  1 Hz updates, the bar. Its file-watcher thread polls the config about twice a second
  (upstream behaviour).
- **The daemon's live wakeups vary with what the owner runs.** At 00:50, with the same pearl
  and a quiet machine: 9.4/s on all threads. Tonight: 20-27/s, of which only about 1/s is
  topic traffic. The rest are file-watch and request events. It holds 13 inotify instances
  with about 97 watches: settings and state folders, `~/.config`, the Brain vault for
  recent notes. Pinning down the exact sources needs strace on a test host.

## Top remaining costs

1. **Big-panel animation frames (Bead + Shell).** A 12-20 ms gap at the start of most large-panel
   transitions (Bead first-frame pacing), plus dashboard mid-motion misses. This is v0.1 blocker
   #12. The compositor's frame 3-5 waits are gone since NN0045 (no wait over 9.5 ms).
2. **Interaction CPU and memory after first use (Bead).** The shell's `bead-worker` render thread
   is about half of Nacre's interaction CPU (2.6 % of a core). Drawing is CPU raster; Noctalia
   uses the GPU. Memory grows +43 MiB after the first panel opens: caches kept warm.
3. **Video wallpaper (Shell + Bead; the compositor has no extra cost).** Every video frame is a
   full-output composite in nacre-niri, which costs the same as stock niri (NN0052). Turning on
   wallpaper blur adds +145 % (upstream re-blurs every frame). Levers are on the shell side: a
   lower frame rate cap, pausing while covered, and screen-sized sources (N0337).

Smaller: the deploy build's on-disk size (Release; packages are stripped). The daemon's
file-watch wakeups under heavy use (Platform, needs a test host). nacre-niri's 2 Hz config
poll (upstream).

## How the daemon works

- **One binary.** `nacre-daemon` is the Rust `nacre-helper` binary run as the user service
  "Nacre desktop state service". It owns desktop state, so the shell only draws.
- **One event loop for 38 services.** Battery, audio, network, Bluetooth, notifications, tray,
  dashboard data, settings stores, recorder, wallpaper and more all run as tasks on one
  current-thread runtime on the main thread.
- **Supervision.** A failed service is restarted alone, with a backoff starting at 250 ms. The
  others keep running.
- **Topics.** A hub owns the state of 69 topics. Clients (the shell, `nacrectl`) connect over
  one Unix socket (`$XDG_RUNTIME_DIR/nacre/daemon.sock`). They subscribe, get a snapshot, then
  changes, with bounded per-client queues and publishes coalesced per 16 ms frame. The hub has
  no timer polls.
- **Methods.** The shell calls 132 methods over the same socket: settings writes, AI chats,
  Brain search and others.
- **Event-driven by default.** Sources push changes: D-Bus signals (for example UPower for the
  battery, systemd for the recorder), PipeWire, inotify on config, state and Brain folders,
  and compositor IPC events. Samplers that must poll, such as CPU and memory for the
  dashboard, run only while a client subscribes.
- **Blocking work stays off the event loop.**
  - `nacre-audio` is the one PipeWire client for the whole desktop (N0314).
  - `nacre-fast-daemon` is an independent lane for one-shot hardware requests such as
    the volume and brightness keys.
  - `nacre-offload`, plus a 2-thread blocking pool, takes file and sensor reads such as GPU
    sensors and the process list.
- **Footprint.** About 0.4-0.5 % of a core and 53-58 MiB PSS in real use tonight. 0.68-1.0 s
  from start to ready.
